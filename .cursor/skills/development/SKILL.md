## 一、代码规范

### 1.1 代码风格

**规范遵循**：
- **前端**：遵循 ESLint + TypeScript 官方规范
- **后端**：严格遵循阿里巴巴 Java 开发规约（Alibaba Java Coding Guidelines）

#### 阿里巴巴 Java 开发规约（后端）

| 规则类别 | 说明 |
|----------|------|
| 命名风格 |驼峰命名、类名大写开头、方法名小写开头等 |
| 常量定义 |不允许魔法值、必须使用常量类 |
| 代码格式 |缩进、换行、大括号位置等 |
| 集合处理 |注意集合是否为null或空 |
| 并发处理 |线程安全、锁的使用 |
| 控制语句 |必须使用大括号、禁止复杂条件嵌套 |
| 异常处理 |禁止捕获通用异常、必须记录日志 |
| 日志规范 |使用正确的日志级别、禁止使用System.out |
| 单元测试 |必须编写单元测试 |
| MySQL规约 |建表规范、索引规范、SQL规范 |
| 异常处理 |禁止直接捕获、必须向上抛出 |

#### 前端代码风格（Vue3 + TypeScript）

```typescript
// 命名规范
// 组件名：PascalCase
const UserProfile = defineComponent({ ... })

// 函数名：camelCase
function getUserInfo() { ... }

// 常量：UPPER_SNAKE_CASE
const MAX_RETRY_COUNT = 3

// 类型/接口：PascalCase
interface UserInfo {
  id: string
  name: string
}

// 文件名：kebab-case
// user-profile.vue
// user-profile.ts
// useUserInfo.ts
```

#### 后端代码风格（Java + Spring Boot）

```java
// 类名：PascalCase
public class UserService { ... }

// 方法名：camelCase
public UserInfo getUserInfo() { ... }

// 常量：UPPER_SNAKE_CASE
public static final int MAX_RETRY_COUNT = 3;

// 变量名：camelCase
private String userName;

// 包名：全小写
package com.company.project.module;
```

### 1.3 注释规范

**注释率要求**：代码注释率不低于 **20%**

**注释率计算方式**：
```
注释率 = (注释行数 / (代码行数 + 注释行数)) × 100%
```

#### AI 生成代码标记规则

**所有 AI 生成的代码必须遵循以下标记规则**：

| # | 规则 | 说明 |
|---|------|------|
| 1 | **必须**使用 `Generated By AI Start` 标记开始 | 在新增代码块前添加一行注释 |
| 2 | **必须**使用 `Generated By AI End` 标记结束 | 在新增代码块后添加一行注释 |
| 3 | **必须**使用模型名称替换占位符 | 如 `Generated By AI Start (Sisyphus)` |
| 4 | **必须**检查标记是否正确添加 | 确保标记成对出现 |
| 5 | **禁止**使用行尾注释 | 统一使用块注释 |
| 6 | **禁止**生成过多空行 | 非必要不生成空行，保持代码紧凑 |

**正确示例**：
```typescript
// Generated By AI Start (Sisyphus)
export function calculateTotal(items: Item[]): number {
  return items.reduce((sum, item) => sum + item.price, 0);
}
// Generated By AI End (Sisyphus)

// Generated By AI Start (Sisyphus)
export function getUserById(id: string): User | null {
  return this.users.find(user => user.id === id) || null;
}
// Generated By AI End (Sisyphus)
```

**错误示例**：
```typescript
// 错误：生成过多空行
export function calculateTotal(items: Item[]): number {

  return items.reduce((sum, item) => {

    return sum + item.price;

  });

}


// 错误：行尾注释
const sum = items.reduce((acc, item) => acc + item.price, 0); // AI生成

// 错误：标记遗漏
export function calculateTotal(items: Item[]): number {
  return items.reduce((sum, item) => sum + item.price, 0);
}
// 缺少 Generated By AI End 标记
```

#### AI 代码块合并规则

**触发合并的条件**（满足任一条件时，合并所有 AI 注释）：

| 条件 | 说明 |
|------|------|
| **相邻标记** | 上一个结束标记和下一个开始标记之间 ≤5 行（不包含空行） |
| **AI 代码率过高** | 整个文件的 AI 代码率 > 80% |

**合并规则**：
- 满足合并条件时，删除所有 `Generated By AI Start` 和 `Generated By AI End` 标记
- 在文件顶部添加文件级 AI 标记

**文件级 AI 标记格式**：
```typescript
// Generated By AI Start (Sisyphus)
// 本文件由 AI 代码生成
// 生成日期：{YYYY-MM-DD}
```

**合并示例**：

合并前（相邻 AI 代码块）：
```typescript
// Generated By AI Start (Sisyphus)
function add(a, b) {
  return a + b;
}
// Generated By AI End (Sisyphus)
// Generated By AI Start (Sisyphus)
function multiply(a, b) {
  return a * b;
}
// Generated By AI End (Sisyphus)
```

合并后：
```typescript
// Generated By AI Start (Sisyphus)
// 本文件由 AI 代码生成
// 生成日期：2024-01-15

function add(a, b) {
  return a + b;
}
function multiply(a, b) {
  return a * b;
}
```

**AI 代码率计算**：
```
AI 代码率 = (AI 生成的行数 / 总代码行数) × 100%
```

## 二、Git 工作流

### 2.1 分支命名规范

```
{类型}/{版本号}-{简短描述}

# 类型
feature/     # 功能开发分支
bugfix/      # Bug修复分支
hotfix/      # 紧急修复分支
release/     # 发布分支
refactor/    # 重构分支

# 示例
feature/v1.0-user-module
bugfix/v1.0-login-issue
hotfix/v1.0-critical-bug
release/v1.0
refactor/v1.0-optimize-query
```

### 2.2 Commit 规范

#### Commit 消息格式

```
{类型}({范围}): {简短描述}

# 示例
feat(user): add user login functionality
fix(order): resolve order creation error
docs(api): update API documentation
style(ui): adjust button styles
refactor(service): optimize user query
test(unit): add user service tests
chore(deps): update dependencies

# 详细描述（可选）
# 空行
# 详细描述说明

# Breaking Changes（可选）
BREAKING CHANGE: {描述}
```

#### Commit 类型

| 类型 | 说明 |
|------|------|
| feat | 新功能 |
| fix | Bug修复 |
| docs | 文档更新 |
| style | 代码格式（不影响功能） |
| refactor | 重构 |
| perf | 性能优化 |
| test | 测试相关 |
| chore | 构建/工具相关 |
| build | 构建系统相关 |
| ci | CI配置相关 |

```

    │
    ├── release/v1.0 ──────────────────┐
    │                                   │

    │                               │  │
    │   从 master 创建               │  │

    │                               │  │

## 三、测试要求

### 3.1 测试类型

| 测试类型 | 覆盖率要求 | 执行时机 |
|----------|------------|----------|
| 单元测试 | **代码覆盖率 ≥80%，新增代码覆盖率 ≥80%** | 每次提交前 |
| 集成测试 | ≥60% | 合并前 |
| 端到端测试 | 核心流程覆盖 | 发布前 |

### 3.2 单元测试规范

#### 测试文件命名

```
# 前端
{文件名}.spec.ts
{文件名}.test.ts

# 后端
{类名}Test.java
{类名}ServiceTest.java
```

#### 测试结构（AAA 模式）

```typescript
// Arrange - 准备测试数据
// Act - 执行被测试的方法
// Assert - 验证结果

describe('UserService', () => {
  it('should return user info when user exists', () => {
    // Arrange
    const userId = '123'
    const mockUser = { id: '123', name: 'Test User' }
    
    // Act
    const result = userService.getUserInfo(userId)
    
    // Assert
    expect(result).toEqual(mockUser)
  })
})
```

```java
@Nested
class UserServiceTest {
    
    @Test
    void shouldReturnUserInfoWhenUserExists() {
        // Arrange
        String userId = "123";
        User mockUser = new User("123", "Test User");
        
        // Act
        User result = userService.getUserInfo(userId);
        
        // Assert
        assertEquals(mockUser, result);
    }
}
```

### 3.3 测试命名规范

```
# 前端
it('should {expected behavior} when {condition}')
shouldReturnUserInfoWhenUserExists
shouldThrowErrorWhenUserNotFound

# 后端
should{ExpectedBehavior}When{Condition}
shouldReturnUserInfoWhenUserExists
shouldThrowExceptionWhenUserNotFound
```

### 3.4 测试通过标准

| 标准 | 要求 |
|------|------|
| 测试用例通过率 | 100% |
| 覆盖率 | 满足要求的覆盖率 |
| 无测试警告 | 所有测试必须通过，无 skipped |
| 测试隔离 | 测试间无依赖，可独立运行 |

#### 部署方式说明

##### Docker 部署

**全量部署（从0开始）**：
```bash
# 1. 构建新镜像
docker build -t {镜像名}:{版本号} .

# 2. 停止并删除旧容器（如有）

docker-compose up -d

# 4. 验证
docker ps | grep {镜像名}

**更新部署（增量更新）**：
```bash

docker ps | grep {镜像名}
curl -f http://localhost:{端口}/health
```

##### Kubernetes 部署

**全量部署（从0开始）**：
```bash
# 1. 构建并推送镜像
docker build -t {镜像仓库}/{镜像名}:{版本号} .
docker push {镜像仓库}/{镜像名}:{版本号}

# 2. 删除旧部署（如有）
kubectl delete -f k8s-deployment.yaml

# 3. 部署新版本
kubectl apply -f k8s-deployment.yaml

# 4. 验证
kubectl get pods -l app={应用名}
kubectl describe deployment {应用名}
```

**更新部署（增量更新）**：
```bash
# 1. 构建并推送镜像
docker build -t {镜像仓库}/{镜像名}:{版本号} .
docker push {镜像仓库}/{镜像名}:{版本号}

│                                     │
│ 提交用户：[用户名/姓名]              │
│ 提交邮箱：[邮箱地址]                 │
│ 提交分支：[分支名]                   │
│ 提交类型：[feat/fix/refactor/...]   │
│                                     │
│ 请确认信息是否正确？"               │
│ A. 确认提交                         │
│ B. 修改信息                         │
└─────────────────────────────────────┘
```

**如果用户选择修改**：请用户提供正确的信息后重新确认。

### 8.3 提交执行

确认用户信息后，执行以下操作：
1. 配置 Git 用户信息（仅本次提交）
2. 添加代码到暂存区
3. 提交并添加规范化的提交信息
4. 推送到远程分支（如需要）
5. 记录提交结果反馈给用户

### 8.4 提交信息规范

```
{类型}({范围}): {简短描述}

# 示例
feat(user): add user login functionality
fix(order): resolve order creation error
docs(api): update API documentation
style(ui): adjust button styles
refactor(service): optimize user query
test(unit): add user service tests
chore(deps): update dependencies
```

## 硬性要求汇总

1. **开发前**：必须确认设计文档存在且评审通过
2. **开发中**：必须遵守代码规范和格式化要求
3. **测试**：必须编写单元测试，代码覆盖率和新增代码覆盖率均不低于80%
4. **自检**：提交前必须完成本地自检
5. **PR**：必须创建 PR 并通过代码审查
6. **文档**：代码变更必须同步更新文档
7. **发布**：必须通过所有门禁检查并获得审批
8. **提交确认**：开发完成后必须询问用户是否提交
9. **用户信息**：提交时必须确认提交用户信息
10. **门禁通过**：所有检查必须通过才能合并
11. **部署验证**：合并分支后必须进行部署验证
