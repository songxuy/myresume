## 版本号确认

### 确认时机

在开始设计之前，必须与用户确认版本号。

### 确认规则

1. **已有需求文档时**
   - 版本号**必须**与需求设计说明书保持一致
   - 例如：需求文档为 `需求设计说明书_v2.0.md`
   - 则设计文档为 `详细设计说明书_v2.0.md`

2. **无需求文档时**
   - 请用户输入版本号
   - 询问：`"请输入本次设计的版本号（如 v1.0）："`

3. **通用确认话术**
   ```
   "在开始设计之前，请确认版本号：
   
   版本号：{版本号}
   
   请确认是否正确？（确认后开始设计）"
   ```

### 硬性要求

**禁止在未确认版本号的情况下开始设计。**

### 2.2 数据库设计

**数据库类型**：PostgreSQL

#### 2.2.1 ER 图规范

```
┌─────────────┐       ┌─────────────┐
│   users    │       │   orders    │
├─────────────┤       ├─────────────┤
│ id (PK)    │──┐    │ id (PK)     │
│ username    │  │    │ user_id(FK) │──┐
│ email       │  └──▶│ total_amount│  │
│ created_at  │       │ status      │  │
└─────────────┘       │ created_at  │◀─┘
                       └─────────────┘
                              │
                              ▼
                       ┌─────────────┐
                       │ order_items│
                       ├─────────────┤
                       │ id (PK)    │
                       │ order_id   │
                       │ product_id │
                       │ quantity   │
                       │ price      │
                       └─────────────┘

PK = 主键（应用层生成）FK = 外键
```

**命名规范**：
| 类型 | 规范 | 示例 |
|------|------|------|
| 表名 | 小写下划线，复数名词 | `users`, `order_items` |
| 主键 | `id` (由算法决定) | `id`, `user_id` |
| 外键 | `{引用表名}_id` | `user_id`, `order_id` |
| 索引 | `idx_{表名}_{字段}` | `idx_users_email` |
| 唯一索引 | `uk_{表名}_{字段}` | `uk_users_email` |
| 时间戳 | `{create/update}_at` | `created_at`, `updated_at` |
| 布尔字段 | `is_{xxx}` | `is_active`, `is_deleted` |

**主键生成规范**：
- **禁止使用数据库自增主键**
- 主键由应用层代码生成（具体算法根据场景选择）
- 数据库仅存储主键值（类型由算法决定：UUID → VARCHAR(36)，Snowflake → BIGINT）
- 设计时必须明确主键算法和存储类型

#### 2.2.2 表设计模板

```markdown
### {表名}

| 字段名 | 类型 | 约束 | 说明 |
|--------|------|------|------|
| id | {算法类型} | PK | 主键（应用层生成） |
| ... | ... | ... | ... |
| created_at | TIMESTAMPTZ | NOT NULL, DEFAULT NOW() | 创建时间 |
| updated_at | TIMESTAMPTZ | NOT NULL, DEFAULT NOW() | 更新时间 |

**主键生成**：
- 算法：{UUID / Snowflake / 其他}
- 类型：{VARCHAR(36) / BIGINT / 其他}
- 由应用层代码生成，数据库不负责自增

**索引**：
- `idx_{表名}_{字段}` ON ({字段})

**外键**：
- `fk_{表名}_{引用表}` REFERENCES {引用表}(id)

**说明**：
- [表用途说明]
```

#### 2.2.3 PostgreSQL 特有约束

1. **主键类型**
   - 主键由**应用层代码生成**（如 Java UUID、Snowflake 算法）
   - 数据库存储类型由算法决定：
     - UUID 算法 → `VARCHAR(36)` 或 `UUID`
     - Snowflake 算法 → `BIGINT`
     - 其他算法 → 根据实际长度确定
   - **禁止使用数据库自增主键（SERIAL、BIGSERIAL）**
   - 设计时必须明确指定主键算法和存储类型

2. **时间戳**
   - 使用 `TIMESTAMPTZ` 类型存储时间
   - 必须有 `created_at` 和 `updated_at`

3. **JSON 字段**
   - 灵活字段使用 `JSONB` 类型
   - 定期访问的字段不使用 JSON

4. **枚举类型**
   - 有限状态集使用 `CHECK` 约束
   - 示例：`status VARCHAR(20) CHECK (status IN ('pending', 'completed'))`

5. **全文搜索**
   - 需要全文搜索的字段使用 `TSVECTOR`
   - 建立对应的 GIN 索引

6. **数据库约束**
   - 每张表必须有主键
   - 主键值由应用代码生成，数据库不负责自增
   - 外键必须命名清晰：`fk_{表名}_{引用表}`
   - 敏感字段必须加密或使用 `pgcrypto`
   - 大表必须考虑分区表策略

### 2.3 API 接口设计

#### 2.3.1 RESTful 规范

| 方法 | 用途 | 示例 |
|------|------|------|
| GET | 查询资源 | `GET /users` |
| POST | 创建资源 | `POST /users` |
| PUT | 更新资源（完整） | `PUT /users/{id}` |
| PATCH | 更新资源（部分） | `PATCH /users/{id}` |
| DELETE | 删除资源 | `DELETE /users/{id}` |

#### 2.3.2 URL 命名规范

```
# 正确
GET    /users              # 资源列表
GET    /users/{id}         # 单个资源
POST   /users/{id}/orders # 用户下的订单
GET    /users/{id}/orders  # 获取用户的所有订单

# 错误
GET    /getUsers
POST   /createUser
PUT    /updateUser
DELETE /deleteUser
```

#### 2.3.3 API 文档模板

```markdown
### {接口名称}

**请求**
- **方法**：`{GET|POST|PUT|PATCH|DELETE}`
- **路径**：`{路径}`
- **Headers**：
  | Header | 类型 | 说明 | 必填 |
  |--------|------|------|------|
  | Authorization | string | Bearer Token | 是 |

**请求参数**

| 参数名 | 类型 | 位置 | 说明 | 必填 |
|--------|------|------|------|------|
| id | number | path | 资源ID | 是 |

**请求体**（如适用）
```json
{
  "field1": "value1",
  "field2": "value2"
}
```

**响应**
```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| code | number | 状态码 |
| message | string | 状态信息 |
| data | object | 响应数据 |

**错误码**：
| code | 说明 |
|------|------|
| 400 | 请求参数错误 |
| 401 | 未授权 |
| 404 | 资源不存在 |
| 500 | 服务器错误 |
```

#### 2.3.4 API 设计约束

1. **版本控制**
   - URL 必须包含版本号：`/api/v1/users`
   - 版本变更时，旧版本需保留并标注废弃时间

2. **分页规范**
   - 列表接口必须支持分页
   - 使用 `page` + `page_size` 参数
   - 响应必须包含总数

3. **错误处理**
   - 所有错误必须返回统一格式
   - 错误码必须明确含义
   - 禁止在错误信息中泄露敏感信息

4. **安全性**
   - 敏感操作必须验证
   - 禁止在 URL 中传递敏感参数
   - 禁止 GET 请求修改数据

#### 2.4.2 组件设计约束

1. **单一职责**
   - 每个组件只负责一件事
   - 组件内部禁止有多个不相关的功能

2. **接口隔离**
   - 组件对外接口必须清晰、稳定
   - 禁止暴露内部实现细节

3. **可复用性**
   - 通用逻辑必须抽离为可复用组件
   - 复用组件必须独立于具体业务

4. **可测试性**
   - 每个模块/组件必须可独立测试
   - 必须提供 mock 接口

## 六、设计版本追溯要求

### 6.1 版本管理原则

1. **每个版本独立完整**
   - 每个版本的设计文档必须是完整的
   - 包含该版本的所有设计内容

2. **版本间可追溯**
   - 新版本必须参考历史版本
   - 必须记录与历史版本的差异

3. **版本号规范**
   - 格式：`v{主版本}.{次版本}`（如 v1.0、v2.1）
   - 主版本：重大架构变更
   - 次版本：功能迭代/优化
   - **增量变更版本号与原版本保持一致**

4. **版本号使用场景**
   | 场景 | 版本号规则 |
   |------|------------|
   | 新项目首次设计 | v1.0 |
   | 功能迭代/优化 | 次版本递增（如 v1.0 → v1.1） |
   | 重大架构变更 | 主版本递增（如 v1.x → v2.0） |
   | 增量变更文档 | 目标版本号（如 v1.0 → v1.1 的变更文档为 v1.1） |

### 6.2 版本追溯要求

**每个版本设计必须包含**：
1. 基于前版本的变更说明
2. 功能继承与扩展列表
3. 确保不脱离原有设计范围
4. 版本变更记录

### 6.2 接口详细设计

#### OpenAPI 3.x 注释规范

**暴露给外部的接口**，必须使用 OpenAPI 3.x 注解，包含以下四个必需部分：

| 必需部分 | 说明 | 示例 |
|----------|------|------|
| **接口说明** | 接口功能描述 | `@operation summary` |
| **参数说明** | 请求参数详细说明 | `@parameter`, `@RequestBody` |
| **返回数据样例** | 响应 JSON 示例 | `@ApiResponse` |
| **字段说明** | 返回字段含义 | 响应 JSON 中的注释 |

**Java OpenAPI 3.x 注解示例**：

```java
@RestController
@RequestMapping("/api/v1/users")
@Tag(name = "用户管理", description = "用户相关接口")
public class UserController {

    /**
     * 获取用户详情
     * @param userId 用户ID
     * @return 用户信息
     */
    @Operation(
        summary = "获取用户详情",
        description = "根据用户ID获取用户的详细信息，包括基本信息、角色等"
    )
    @ApiResponses({
        @ApiResponse(
            responseCode = "200",
            description = "成功返回用户信息",
            content = @Content(
                mediaType = "application/json",
                schema = @Schema(implementation = UserResponse.class),

### 10.4 增量变更文档使用说明

1. **何时使用**：当设计发生版本迭代时（如 v1.0 → v1.1），使用增量变更文档记录变更内容
2. **与完整文档关系**：
   - 完整文档（详细设计说明书）是基线
   - 增量变更文档记录从上一版本到当前版本的变更
   - 变更完成后，合并到详细设计说明书
3. **版本管理**：
   - **版本号为变更后的目标版本**（如 v1.0 → v1.1 的变更，使用 v1.1）
4. **存档**：
   - 所有增量变更文档必须存档
   - 保留完整的版本变更历史
